# 开发日志

按时间记录开发过程中做了什么、遇到什么问题、如何解决。严格的验收数据与证据在 [TEST_REPORT.md](TEST_REPORT.md)，环境与 SDK 事实在 [ENVIRONMENT.md](ENVIRONMENT.md)，V1.1 加固细节在 [V1.1_HARDENING.md](V1.1_HARDENING.md)。

## 项目目标

输入一个 B 站视频链接（或 BV 号），工具自动提取**音频**和**关键画面 PDF**，新建一个 NotebookLM 笔记本并上传这两个来源，等待 READY 后输出笔记本链接。转录与总结全部由 NotebookLM 完成，本地不运行 Whisper、OCR 或任何大模型。

## 2026-11-08

### Gate 0：环境与骨架
- 开发机为 Apple Silicon Mac。系统 Python 版本过新（3.15），项目用 uv 管理独立的 Python 3.12；依赖锁定在 `uv.lock`。
- 建立 `.gitignore`：凭证、Cookie、媒体、PDF、任务库等不进入版本库。过程中发现一个反例：未加锚点的 `media/` 规则会误挡源码目录 `src/bili2nb/media/`，改为只匹配根目录运行时目录。
- 所有与 NotebookLM SDK（`notebooklm-py` 0.8.6，**非官方**）打交道的代码集中在 `notebook/adapter.py`，SDK 失效时只需改这一处。

### Gate 1：连接 NotebookLM
- 登录由使用者在浏览器中自行完成，工具不接触密码与 Cookie；登录状态由 SDK 保存在用户主目录的 `.notebooklm` 下，不在项目目录内。
- 真实上传暴露的现象：**服务端已收下文件，但 HTTP 回执丢失**，SDK 报 `NetworkError`；PDF 则在注册后卡在 PREPARING。教训：报错后不能立即重传，必须先核对云端；由此形成"先核对、再决定是否重传"的上传逻辑，并加了回归测试。
- 改用 SDK 的 `curl_cffi` 传输（浏览器级 TLS 指纹）后上传恢复正常；该传输在 SDK 中标注为试验性质，已记入风险。

### Gate 2：`convert`
- 音频：yt-dlp 只取 m4a/AAC 音频流，AAC/MP3 原样保留，不重新压缩；超过 NotebookLM 单文件 200 MB 上限才转码，绝不截断。
- 选帧：OpenCV 低分辨率缩略图做"稳定幻灯片"检测，过滤全黑与重复帧；检测页数过少时补充定时取帧并给出 warning；PySceneDetect 仅用于 `--frames scene`。
- PDF：ReportLab 生成，封面含标题/时长/原链接，每页一张截图并带可点击的时间戳与书签。
- 发现并修复：视频短于 15 秒时定时取帧得到 0 帧；B 站对不存在的视频/分 P 报错不清晰（改为先用公开接口预检）；分 P 标题重复与 CID 缺失。

### Gate 3：`import` 与重复建本
- 任务库（SQLite）按阶段打检查点：`created → converted → notebook_created → uploaded → ready → done`；幂等键为（视频 BV+CID、账号、模式）；对限流/网络错误做有上限的指数退避（最多 5 次）。
- 真实导入暴露**重复建本**：SDK 的自动重试重发了非幂等的"创建笔记本"。修复：创建时关闭 SDK 内部重试，并在连接中断后先核对再决定（先写失败测试再修）。
- 修复后一度仍偶发重复建本，后在 Gate 4 找到更底层原因（见下）。

## 2026-11-09

### Gate 4：可靠性、选图质量、跨平台
- 三类真实样本（屏幕教程 6 分钟、口播 20 分钟、PPT 讲座 38 分钟）完成 benchmark；PPT 样本人工建立参照清单后，召回 14/14，重复页 0（修复烧录字幕导致的误判前：重复率 24%）。
- **大文件上传**：单请求上传在部分网络下约 8 秒被断开，但服务端往往已收下。改为 2 MB 分块的断点续传（`chunked_upload.py`），每块失败先 `query` 服务端偏移再续传，每块最多 4 次。
- **重复建本的真正原因**：libcurl 在"被复用的长连接无响应断开"时会**静默重发 POST**；Google 常常处理完请求才断开，于是创建被执行两次（上传时每次多出一个卡住的"孪生"来源也是同一原因）。用本地探针复现（服务端收到 2 次 POST，强制新连接后为 1 次）并修复。
- 其他修复：PDF 封面中文字体未嵌入导致 NotebookLM 预览乱码 → 嵌入 TrueType 字体子集；`opencv-python` 与 `opencv-python-headless` 同装冲突 → 用 uv override 去掉前者。

### Gate 5 与体验改进
- 取消手机端 NotebookLM 作为必验项；最终标准为：CLI 自动完成导入、两来源 READY、网页版可正常问答。
- 增加 yt-dlp 式用法：`bili2nb <链接或BV号>` 直接导入；首次使用引导设置工作目录与 Google 登录；各系统有默认工作目录且可修改。
- 增加 `bili2nb doctor`（环境自检）、Windows/Linux 适配（嵌入字体候选、默认登录浏览器、UTF-8 文本 IO）。
- 增加 GitHub Actions（macOS / Windows / Linux），实际抓到并修复多个平台相关的测试基础设施问题（见 TEST_REPORT）。
- 仓库公开，MIT 许可证。

### 经验小结
- 对非幂等操作（创建笔记本、注册来源）：**先核对云端状态，再决定是否重试**；禁止盲目重试。
- 客户端报错 ≠ 操作失败：服务端可能已处理完成，只是回执丢失。
- 只验证"文字可提取"不足以发现字体未嵌入问题；视觉验证要在目标应用里看。
- 每个真实线上缺陷都先写失败测试再修复，防止回归。

## V1.2：跨平台登录与多 P 批量导入（2026-11-09 起）
- 设计先行：[V1.2_DESIGN.md](V1.2_DESIGN.md)（核实了 SDK 0.8.6 的登录选项、`get_account_limits`、cookies extra）。
- 登录：三平台默认 Chromium，并由本工具接管一次性下载（可见进度、30 分钟超时、可操作的失败提示）。本机验证中发现：Node 版 `playwright install` 在本机网络下反复在 0% 断开，而 curl 能下同一文件——正好验证了"下载失败要有明确重试/回退指引"这一设计点。macOS 27 上捆绑 Chromium 可正常启动（有窗口与无头）。
- 多 P：一次 view-API 调用取全部分 P；逐 P 转换（`<BV>/P01_标题/`，以 CID 为缓存身份）；先转换、规划、必要时合并，再创建**一个**笔记本；上传计划冻结后逐来源检查点。单 P 沿用 V1.1 已验证的路径，只有多 P 走新引擎。
- 经验：规划类逻辑做成纯函数先写测试（来源额度、合并分组），比在导入流程里边写边试可靠得多。

## V1.2.1 真实验证：20 个分 P（2026-11-10）
- 用 `--part 8-27` 从 132 个分 P 的合集里取连续 20 集（约 2.9 小时）真实导入：1 个笔记本、40 个来源全部 READY，云端标题 40/40 一致，重跑复用。总耗时 36 分钟，其中上传 27 分钟（逐来源串行上传是瓶颈；3 次瞬时网络错误由“先核对再重试”自愈，未产生重复来源）。
- 网页问答：用户在 NotebookLM 里问了 4 类问题（来源可打开、语音内容、画面信息点、跨分 P），反馈“可以答对”（概括反馈，未逐题记录引用了哪些来源）。V-2 整体标 PASS。
- 经验：这次没有暴露新缺陷；但“上传占 75% 时间”说明未来若要提速，应优先考虑并行上传（尚未做，需单独评估 NotebookLM 的并发限制）。

## V1.2 真实验证 V-2（2026-11-10）
- 第一次真实多 P 导入就抓到 Mock 测不出的严重缺陷：任务报 `completed`/4 个来源，云端实际只有 2 个。根因是“多 P 文件同名 + 标题重命名不可靠 + 按文件名复用”。先写失败测试（真实 `NotebookAdapter` 加仿线上行为的假 SDK 客户端）再修；同时补了三道防线：拒绝重复来源 ID、READY 后核对云端、复用已完成任务前核对云端。
- 追加加固：每个分 P 用唯一文件名上传（同目录硬链接，上传后删除），从根上消除“按文件名认来源”。成本低、与 `taken` 保护互补。
- 复验又遇到 NotebookLM 把几乎无语音的音频处理为 ERROR；工具如实失败并给出 retry。经验：Mock 的 adapter 若自带实现，会绕过真实 adapter 的逻辑，关键路径的测试要用真实 adapter + 假 SDK；挑真实验证用的视频必须有大量语音。
- 详见 [TEST_REPORT.md](TEST_REPORT.md) “V-2 真实多 P 导入记录”。

## V1.2.2：`--merge-sources`（2026-11-10）
- 起因：V-2 第三次上传 40 个来源用了 27 分钟。先做离线分析（[V1.2_MERGE_SOURCES.md](V1.2_MERGE_SOURCES.md)）：每个来源约 6–8 个与大小无关的请求，合并把 ≈280 个降到 ≈14，数据块请求 ≈100 → ≈82；但历史数据点（每来源平均大小几乎相同）**无法把固定开销与字节吞吐分开**，所以提速幅度只能给区间（预期 0%–85%），需要真实试验。
- 实现：先写 20 项失败测试，再加 `planner.plan_uploads(merge=)`、`Importer.run(merge_sources=)`、`import --merge-sources`；`merge_requested` 记入计划（冻结）与 `--json`；任务键不变。569 项测试全绿。

## V1.2.3：最小合并 + `--source-limit`（2026-11-10）
- 起因：`--merge-sources` 的真实试验显示，本机到 Google 的网络会在传输中途断开，一个 122 MB 的合并音频连续失败 4 次、22 分钟没传完；小文件断一次损失很小。产品所有者决定：默认逐 P；超限时只合并到刚好不超限；测试时把账号当成“50 来源的免费用户”，即 25 组、每组同时有音频和 PDF。
- 过程：先按“PDF 优先、音频逐 P”做了第一版并提交（`aa15e13`），随后按新要求整体替换为**对齐的均衡分组**：把分 P 切成 g 个大小相差 ≤ 1 的连续组，每组音频、PDF 各 1 个来源且边界一致，g 取使来源总数 ≤ 上限的最大值；组内合并文件超 190 MiB 则对半拆（音频与 PDF 一起）；无 PDF 的分 P 不进 PDF 来源；最少来源数仍超限则建本之前以退出码 27 失败。计划新增 `merge_mode`（`minimal` / `fewest`）、`merge_group_count`、`merge_group_sizes`；`--merge-sources` 不变。
- 新增 `import --source-limit N`（N ≥ 2）：有效上限 = `min(账号上限, N)`，只更严；`limit_origin` 记为 `override`；非法值在任何网络调用之前报 `INVALID_URL`；已有同一选择的任务时沿用原计划并提示；不改变任务键。
- 旧测试：`test_planner` 中三条断言“超限就并成最少”的测试按新语义重写；`test_multi_import::test_over_quota_merges_but_still_creates_one_notebook` 改为对齐分组（上限 4、3 个分 P → `P01+P02` 与 `P03` 各有音频和 PDF，共 4 个来源）并新增上限 2（一组）的端到端用例；其余见 `tests/unit/test_source_limit.py`。613 项离线测试全绿。

## V1.2.4：导入后精确清理 + `bili2nb clean`（2026-11-10）
- 起因：产品所有者要求"所有成功上传的内容不要继续保留在本地，整个任务结束并确认笔记本已添加全部来源后再清理"。旧实现 `rmtree(job.output_dir)` 在多 P 任务里会删掉整个 `<BV>/`，包括用户用 `convert` 生成、本次没选中的分 P；清理也不以云端核对为前提；失败 / 被取代任务的遗留文件无处清理。
- 做法（TDD，新增 `tests/unit/test_cleanup.py` 26 项，全部离线、仅用 `tmp_path`）：新增 `bili2nb/cleanup.py`（精确范围、输出根内校验、符号链接跳过、失败只警告、批次清单重建）；`Importer._cleanup` 改为"仅当本次云端核对通过才清"——多 P 用 `_m_finalize` 的成功标记，单 P 新增只读 `list_sources` 核对；任务 JSON 新增 `cleanup`，普通输出一行说明释放空间；新增 `clean`（dry-run 默认、`--yes`、`--json`、可点名 job id）。
- 旧测试：仅 `test_import_jobs.FakeNotebookLM.list_sources` 由恒返回 `[]` 改为返回真实存在的来源；其余不变。离线测试 639 项全绿，ruff 干净。
- 未做：真实导入后的清理未在真实 NotebookLM 上观察；`clean` 不联网核对云端（核对未通过的任务只在点名 job id 时才删）。
