# V1.2 设计：跨平台登录 + B 站多 P 批量导入

状态：**已按本设计实施（见文末"实施记录与偏差"），待审查。** 基线：V1.1（`bb40d24`），`notebooklm-py==0.8.6` 不升级。

本文区分三类内容：**已核实**（读过本机安装的 SDK 0.8.6 源码或本项目代码）、**决策**（我做的取舍）、**待验证**（实施时要用真实环境确认）。

## 0. 目标与非目标

目标：
1. 登录默认走 Playwright Chromium，不要求用户预装 Chrome / Edge。
2. 一个 B 站链接（未指定 P）= 全部分 P → 每 P 独立音频 + PDF → **只建一个**笔记本 → 全部来源 READY。

非目标（保持 V1.1 约束）：Docker、Chrome 扩展、字幕、Bot、GUI、多笔记本自动拆分、升级 SDK、任何 AI 依赖、改变 `bili2nb <URL>` / `convert` / `import` 的用法。

## 2. 登录

### 2.1 已核实的 SDK 事实
- `notebooklm login --browser` 取值 `chromium`（**SDK 自身默认**）/ `chrome` / `msedge`。`chromium` = Playwright 管理的浏览器，缺失时 SDK 自动执行 `python -m playwright install chromium`。
- 本项目依赖已含 `notebooklm-py[browser,impersonate]`，所以 `playwright` 已随包安装（本机 1.64.1）。无需新增依赖。
- **SDK 自动安装的缺点**：输出被捕获（用户看不到进度），超时固定 **300 秒**；约 170 MB 的下载在慢网络下可能超时后"Proceeding anyway"，用户看到的是莫名其妙的启动失败。
- SDK 在 `--browser` 的帮助里写明：bundled Chromium 在某些系统（如 macOS 15+）会崩溃，应改用 `chrome`。**本机是 Darwin 27**，这是真实风险，见"待验证 V-1"。
- `--browser-cookies [auto|chrome|firefox|safari|...]` 存在，需要 extra `cookies`（`rookie-cookies>=0.1.0,<1`），读取已有浏览器的 Google Cookie。

### 2.2 决策
1. `default_browser()` 统一返回 `"chromium"`；`setup`、`auth login`、首次引导、AUTH_REQUIRED 后的登录全部走同一个函数。`--browser chrome|msedge` 保留。
2. **自己接管"安装 Chromium"这一步**，不再依赖 SDK 的静默安装：
   - 探测：在子进程里用 playwright 取 `chromium.executable_path` 并检查是否存在。
   - 缺失时先告知：要下载约 170 MB、存放位置（Playwright 用户级缓存目录，不改系统/Chrome/Edge/Safari 配置），再执行 `python -m playwright install chromium`，**继承终端以显示进度**，超时放宽到 30 分钟。
   - 失败：给出明确原因分类与重试方法（重新运行同一命令即可续装；或改用 `--browser chrome|msedge`）。
3. 登录失败的区分：**下载失败 / 浏览器启动失败 / 未完成登录（超时）** 三类消息分开写，都带"重试命令"。我们只能拿到 SDK 的退出码，所以"启动失败 vs 没登录完"靠**安装探测 + 退出码 + 已有 Chrome/Edge 检测**组合判断，措辞用"可能"，不编造精确原因。
4. 交互式终端里 Chromium 启动失败时，若检测到系统有 Chrome/Edge，**询问**是否改用它重试（只提示、不擅自切换，非交互/`--json` 下不询问）。
5. Linux：Chromium 依赖系统库且需要图形会话。无桌面的服务器上登录本来就做不到——文档写明"在有桌面的机器上登录一次"，不假装支持。
6. `doctor` 的 `login-browser` 检查改为：Chromium 是否已装（缺失 = WARN，提示"首次登录时会自动下载"）；Chrome/Edge 变为"可选"信息。

### 2.3 `--browser-cookies auto`：**建议暂缓**
理由（均来自 SDK 源码/帮助文本，未实机验证）：
- 需要新增原生依赖 `rookie-cookies`；它的许可证与各平台 wheel 覆盖**我还没核实**，按项目纪律应先核实再引入。
- 会读取用户真实浏览器里的**全部 Google Cookie**，隐私面显著变大；`SECURITY.md` 与凭证说明需要重写。
- 已知坑：Chrome 在 Windows 的 Cookie 加密、macOS 钥匙串授权弹窗、Safari 需要完全磁盘访问、浏览器未登录或 Cookie 提取不全（SDK 自身就有 "extraction incomplete" 的恢复路径）。每个都是支持负担。
- 收益只是"省一次登录"，而 Chromium 方案已经满足"不依赖预装浏览器"。

结论：V1.2 **不引入** cookies extra，也不透传该参数；README 的"已知限制/后续"写明理由。若你仍想要，我另起设计（先核许可证与三平台实测）。

### 2.4 登录测试
全部离线：mock `subprocess.run` 与探测函数，断言命令行参数（含 `--browser chromium` 默认）、三平台默认一致、显式 chrome/msedge 透传、各失败分类的消息、非交互不提问、不读取/打印凭证文件。
CI 增加一个**可选**小任务：三平台各自用 Playwright **只启动捆绑 Chromium 打开 `about:blank`**（不访问 Google）。诚实说明：GitHub 的 runner 本来就预装了 Chrome/Edge，所以这个任务证明"捆绑 Chromium 能装、能启动"，**不能**证明"没有 Chrome/Edge 的机器可用"。

## 3. B 站分 P 枚举

### 3.1 行为规范
| 输入 | 范围 |
|---|---|
| `BV号` / 无 `p=` 的 URL | 全部 P |
| `?p=N` 或 `--part N` | 仅 P N（URL 优先，沿用现有规则） |
| `--part 8-27` / `1,3,5` / `1-3,7`（V1.2.1） | 仅所选分 P（去重、升序；见 §13 第 7 条） |
| 单 P 视频 | 唯一的 P |

`--part` 最初只接受**单个整数**；V1.2.1 起也接受范围/列表（动机：想在 132 个分 P 的合集里只处理连续 20 集做真实验证），单个数字的行为保持不变。

### 3.2 元数据获取
- 新增 `fetch_video(video_id) -> VideoMeta`：**一次** view API 调用，返回总标题、UP 主、`pages` 全量（`cid`、`page`、`part` 标题、`duration`）。`fetch_view()` 保留为薄封装，现有测试不动。
- 单个 P 的 `VideoInfo` 直接由 `VideoMeta.pages[i]` 构造（时长来自 API），**不再对每个 P 调 yt-dlp `extract_info`**，减少请求与风控概率。
- 下载仍用 yt-dlp + `noplaylist=True` + `?p=N`。
- **防"不同 P 下到同一内容"**：下载后校验音频时长与 API 的该 P 时长一致（`prepare_audio` 已有校验）；再对各 P 音频做内容哈希，出现重复则报错而不是上传。
- 失败情形：
  - view API 不可达或被风控、且未指定 P：用 yt-dlp 的 flat 播放列表枚举兜底（取数量与标题；拿不到 CID 则键用 `BV_p{n}`，与现有行为一致）；仍失败 → 明确报错并提示 `--part N`，**不静默退回 P1**。
  - `cid` 缺失：同上用 `p{n}` 键并给 warning。
  - 视频不存在/已删：沿用现有 `VIDEO_UNAVAILABLE`。
  - 指定的 P 超出总数：沿用现有报错。
  - 限流：每个 P 的转换包在现有 `_backoff`（最多 5 次）里。

## 4. 本地输出布局

```
output/<BV>/
  manifest.json                # 顶层：全部 P 的元数据、状态、文件位置（原子写，每个 P 完成后更新）
  P01_<安全标题>/
    audio.m4a  keyframes.pdf  manifest.json   # 与 V1.1 单 P 产物同构，含 cid
  P02_.../
  _merged/                     # 仅在需要合并时出现
```

- **缓存身份 = CID**（不是目录名）。命中规则：扫描 `output/<BV>/*/manifest.json` 找 `cid` 与 `complete` 相符者；标题变化导致目录名变化也不会重下。
- 目录名宽度按总 P 数补零（至少两位），标题经现有 `safe_name`。
- V1.1 旧产物目录 `output/<BV>_<CID>/` **原样保留、不删除、不迁移**；若其 manifest 完整且 CID 与选项一致，可只读复用。
- 默认成功后清理本地文件的行为不变（`--keep-files` / `--output` 保留）。
- `convert` 与 `import` 共用同一套"逐 P 转换"函数，行为一致；单 P 的 `convert --json` 仍保持旧字段形状，新增 `parts` 数组。

## 5. 任务模型（重点）

### 5.1 取舍：扩展 `jobs` 表，而不是新建 batch 表
备选：新建 `batches` + `batch_parts` 两张表（范式干净，但 `status/retry/jobs/幂等/孤儿清理/--json` 全要双份，且旧任务要再桥接一次）。
**选择**：给 `jobs` 增加两个 JSON 列，**一个 Job = 一个视频的一次导入（可含多个 P）**：

```
parts TEXT NOT NULL DEFAULT '[]'   -- 每个 P 一项
plan  TEXT NOT NULL DEFAULT '{}'   -- 上传计划（冻结后不可变）
```

`parts[i]`：`{part, cid, title, duration, dir, audio_path, pdf_path, visual:{...}, convert:"pending|done|failed", error}`
`plan`：`{strategy:"per_part|merged", source_limit, limit_origin:"server|default", items:[...]}`
`plan.items[j]`：`{key, kind:"audio|pdf", parts:[1..n], path, bytes, title, source_id, ready}`

理由：每个来源的 `source_id`/`ready` 与其**上传条目**绑定（合并后一个来源对应多个 P，所以不能挂在 `parts[i]` 上）；P 的转换状态与上传状态分开记录，互不污染。

### 5.2 幂等键与"不误复用"
- 单 P 选择：`video_key` 沿用 `BV_CID`（因此**旧任务天然被命中**，不会为已导入过的单 P 重新建笔记本）。
- 全部 P（≥2 个）：`video_key = BV_all`，与任何单 P 键不同，**不会误复用旧的 P1 任务**。
- 模式（audio-only / frames 模式）、账号仍在键里。
- 已存在的 `BV_all` 任务发现视频现在的分 P 数与记录不同：**不静默复用**，提示"分 P 有变化，用 `--force-new` 重建"。
- `--force-new`：supersede 旧任务，只新建**一个**笔记本（含完整 P 集合）。旧笔记本和来源**永不删除**。

### 5.3 旧任务兼容
- `_migrate` 追加两列（幂等，沿用现有写法）。
- 旧行 `parts='[]'` 视为"遗留单 P"：读取时**虚拟合成**一个 P 与两个上传条目（`sources.audio/pdf` → 条目 id），首次 `retry` 时按新结构落盘；`status`、`retry`、`jobs`、`--json` 的旧字段（`source_ids`、`source_ready`、`audio_path`、`pdf_path`）继续输出。
- 测试用**真实 V1.1 结构的数据库 fixture**（含已完成、失败、孤儿记录）验证。

### 5.4 阶段（检查点）
```
created → converted(全部P) → planned → notebook_created → uploaded → ready → done
```
- **转换先于建本**：所有 P 转换、文件校验、上传计划可行性，全部通过后才创建云端笔记本。任一 P 下载失败 → 任务 FAILED，**云端无任何资源**，已完成的 P 在下次 `retry`/重跑时从缓存复用。
- **计划冻结**：一旦写入 `notebook_id`，`plan` 不再重算（避免断点续传时额度变化导致来源错位）。建本前允许重新计划。
- 上传按条目顺序，每个条目成功即落库（`source_id`）。中途异常/Ctrl+C：`retry` 只继续没有 `source_id` 的条目；**正在传的那一个**走 V1.1 已有的"先对账、证据驱动的孤儿清理"，不会重复建本或重复传已成功条目。
- READY 等待按条目逐个检查点；某来源被 NotebookLM 拒绝时，只清除该条目的记录并允许重传（沿用现有行为）。

## 6. 上传计划与自动合并

### 6.1 额度来源
`client.settings.get_account_limits()`（**公共 API**，已核实 `AccountLimits.source_limit: int | None`、`tier`）。我们只读不写。
- 取不到（网络错误、`None`）：用 `_backoff` 重试；仍失败 → 回退到**保守默认 50**，计划里标记 `limit_origin:"default"` 并给 warning。保守值只会让我们更早合并，不会超限。
- `sdk_compat` 的能力清单加入该方法；缺失则 `SDK_INCOMPATIBLE`。
- 单文件上限沿用 `MAX_UPLOAD_BYTES` = 200 MiB；**合并组**留余量，目标 ≤ 190 MiB。

### 6.2 策略（决策：只在"必须"时合并，且**只合并到刚好不超限**）
- **A 逐 P**：每个 P 的音频与 PDF 各一个来源（无有效画面的 P 只有音频，+warning；`--audio-only` 只有音频）。来源总数 ≤ 额度 → 采用。
- **B 最小合并**（V1.2.3 起，取代原先的"最少来源"）：A 超额时，按**对齐的均衡分组**合并。把 n 个分 P 按顺序切成 g 个大小相差不超过 1 的连续组（余数分给前面的组）；每组的音频合并成 1 个来源、PDF 合并成 1 个来源，**两者使用完全相同的分组边界**（没有 PDF 的分 P 只是不进 PDF 来源，整组都没有 PDF 就只有音频来源）；单成员的组保持逐 P 的来源与标题。g 取**使来源总数 ≤ 额度 L 的最大值**（从 n 往下找第一个满足的），所以合并得最少、文件最小。来源总数 = 有音频的组数 + 有 PDF 的组数。标题如 `P01-P05｜音频`、`P01-P05｜关键帧PDF`，不连续写 `P01+P03`。计划里记录 `merge_mode: "minimal"`、`merge_group_count` 与 `merge_group_sizes`（音频/PDF 各组的分 P 数）；来源按组排序（先音频后 PDF）。
  - **为什么对齐**：用户要的是"每一组同时有音频和 PDF"（免费账号 50 = 25 组 × 2），这样引用和目录页都自洽（"第 X 组 = P01–P05 的音频和 PDF"），也便于以后在 100+ P 的视频上单独做真实测试。曾考虑过"PDF 优先、音频逐 P"（PDF 体积小、重传代价低），但它会让音频和 PDF 的分组边界不一致，已被对齐方案取代。
  - **为什么改**：原先的 B 是"合并成尽量少的来源"（30 个分 P → 1 个音频 + 1 个 PDF），设计时只算了固定开销，没算网络。真实试验（见 TEST_REPORT）里本机到 Google 的网络会在传输中途断开，一个 122 MB 的合并音频连续失败 4 次、22 分钟没传完；小文件断一次损失很小。所以改为：默认逐 P，超限只合并到刚好不超限。
  - 可选的 `--merge-sources`（V1.2.2）保持"并成最少来源"（`merge_mode: "fewest"`，音频与 PDF 各自独立打包），仅用于上传提速试验。
  - **`--source-limit N`**：测试开关，有效上限 = `min(账号读到的上限, N)`（只更严），`limit_origin` 记为 `override`；用于在付费账号上按免费 50 来源演练。
- **C 合并后超 190 MiB**：该组（音频与 PDF 一起）按分 P 对半拆开，必要时反复拆，拆完的组数计入上面的总数判断；`--merge-sources` 路径则由贪心打包自然拆成多组（即你的"按连续 P 分组"），不是单独的分支。
- **D 仍装不下**（即使全部压到体积上限允许的最少组数仍 > L）：**在创建笔记本之前**以新错误码 `UPLOAD_PLAN_INFEASIBLE`（退出码 27）失败，消息写明：P 数、需要来源数 vs 额度、总大小、建议（缩小范围 `--part N` / 升级账户额度）。**绝不**自动拆成多个笔记本。
- **提前止损**：转换前先用时长做一个**下界估算**（按 64 kbps 这种明显偏低的码率），连下界都装不下就直接失败，免得先下载几十小时素材再失败。真正的判定仍在转换完成后用真实大小。

### 6.3 合并实现
- 音频：先 ffprobe 比对各 P 的编码/采样率/声道，取**多数派**参数。多数派是 AAC/MP3 时，与多数派一致的文件用 ffmpeg concat demuxer **`-c copy`**（无重编码），少数不一致的文件**单独**转成多数派参数后再拼（真实的 30 P 视频里 29 个是 44.1 kHz、1 个是 48 kHz，只转这 1 个）；仅当多数派编码本身不适合时才整体转 AAC，且码率按总时长自适应，保证不超体积上限。合并后必须：`ffprobe` 总时长 = 各 P 时长之和（容差 `max(2s, 0.1%)`）、能完整解码（沿用现有解码校验）、大小 ≤ 上限，否则报错，**不上传**。
- PDF：`pypdf` 合并，每个 P 一个顶层书签，保留其内部时间戳书签；页序 = P 序。PDF 封面里附"各 P 在合并音频里的起始时间表"，弥补 NotebookLM 转录里没有 P 边界的问题。
- 单个 P 的独立文件始终保留在本地；合并文件放 `_merged/`，成功上传后随目录一起按现有规则清理。

### 6.4 来源命名
- 逐 P：`P01｜<分P标题>｜音频`、`P01｜<分P标题>｜关键帧PDF`；合并：`P01-P05｜音频`。≤100 字符截断（沿用现有函数）。
- 单 P 视频**保持 V1.1 命名**（`音频｜<标题>`），与历史笔记本和"同名对账"逻辑一致。
- 名称在笔记本内唯一（P 编号保证），这是上传前"复用同名可用来源"对账的前提。

## 13. 实施记录与偏差（实施后补充）

与上文设计相比，实施时做了这些调整，原因都是"降低风险、保持 V1.1 已验证路径不动"：

1. **单 P 选择继续走 V1.1 的原流程，只有多 P 走新引擎**（§5.3 原计划"旧任务读取时虚拟合成一个 P"）。这样所有旧任务（`parts=[]`）和单 P 导入零改动，既有的 30 多个导入测试一条没改就通过；新引擎只处理多 P（`BV_all`）。代价是两条代码路径，由 `Importer._execute` 按 `job.parts` 是否为空分流。
2. **新增退出码 `PARTS_CHANGED`（28）**：已有的 `BV_all` 任务记录的分 P 列表与现在不一致时报错，要求 `--force-new`，而不是静默复用（设计 §5.2 的"不静默复用"落地）。
3. **合并文件在创建笔记本之前就生成并校验**（设计里写"尽量先完成本地"），所以合并失败（时长不符、超限）也不会在云端留下任何东西。
4. **`plan_uploads` 的体积上限在调用时读取模块常量**，便于测试覆盖超限路径。
5. **CLI `convert` 也走同一套逐 P 循环**（`batch.convert_parts`），`convert --json` 对单 P 保持旧字段形状并新增 `parts` 数组。
6. **磁盘上的单 P 产物目录变为 `<BV>/P01_标题/`**（原为 `<BV>_<CID>/`）。V1.1 的旧目录不动，完整的旧目录会被只读复用。

7. **`--part` 范围/列表语法（V1.2.1）**：`8` / `8-27` / `1,3,5` / `1-3,7`，解析在 `bili2nb/selection.py`（非法写法统一报 `INVALID_URL`、退出码 10，在任何网络调用之前）。
   - 恰好选中 1 个分 P → 仍是单 P 老流程与旧键 `BV_cid`（旧任务继续命中）；选中全部分 P → `BV_all`；其余 → 新键 `BV_P8-27` / `BV_P1-3+7`（规范化压缩写法；超过 48 个字符则改用哈希），与 `BV_all`、任何 `BV_cid` 都不同，对同一选择稳定（`7,1,2` 与 `1-2,7` 是同一任务）。
   - `plan_parts(ref, selection=None)` 仍只调一次 view API，只为所选分 P 构造 `VideoInfo`（`part_count` 仍是总数）；`batch.convert_parts` / `Importer.run` 的 `part` 参数接受数字或写法字符串。`manifest.json` 的 `selection` 为 `all` / `P8` / `P8-27` / `P1-3+7`；`--json` 的 `part_count` 是视频总分 P 数、`selection` 为规范化字符串、`parts` 只含被处理的分 P。
   - 不连续的选择在超额合并时，来源标题写真实成员（`P01+P03+P05`、`P01-P04+P07`），太长则写 `P01…P99（共N个分P）`，不再假装连续区间；来源键保持完整成员以保证唯一。
   - 已有任务与当前选择的分 P/CID 不一致 → 仍报 `PARTS_CHANGED`（同一选择键下 CID 变了）。不同选择是不同任务，不会相互触发。

8. **最小合并（V1.2.3）**：`plan_uploads` 的超限分支由"合并成最少来源"改为"对齐的均衡分组，g 取不超限的最大值"（§6.2）。起因是 V-2 真实试验：本机网络会在传输中途断开，122 MB 的合并音频连续失败 4 次、22 分钟没传完。先实现过"PDF 优先、音频逐 P"的版本，随后按产品所有者的新要求（免费账号 50 来源 = 25 组，每组同时有音频和 PDF）替换为对齐分组。`--merge-sources` 仍是"最少来源"。导入器的合并逻辑不用改（`_build_merged` 按条目是否合并来写 PDF 目录页）；`--json` 的 `upload_plan` 新增 `merge_mode`、`merge_group_count`、`merge_group_sizes`。已冻结的旧计划不受影响。
9. **`import --source-limit N`（V1.2.3）**：见 §6.2；校验在任何网络调用之前（`INVALID_URL`，退出码 10），单 P 导入忽略并提示，不改变任务键。
